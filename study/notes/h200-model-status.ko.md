# H200 모델 현황 (2026-11-25)

보정한 Vortex 모델로 실험을 시작하려는 사람을 위한 문서입니다. 작업 브랜치는 `feature/dxa-borrowing`입니다. 숫자마다 출처를 적었고, "항목 N"은 `upstream-pr-candidates.ko.md`의 N번입니다. 잰 것과 추론한 것은 나눠 적었습니다. 영어판은 `h200-model-status.md`입니다.

## 프로파일과 한 점을 돌리는 법
- **`h200s`**: H200의 6분의 1(SM 22개, HBM3e 스택 하나, 800 GB/s, L2의 6분의 1). 아래의 SM당 수치는 모두 이 프로파일의 SM 하나입니다.
- **`h200g2`**: SM 32개를 16개씩 그룹 둘로, L2 슬라이스 32개를 HBM3e 스택 둘의 채널에 하나씩 묶음(공칭 1.6 TB/s, 연구 목표 1,544 GB/s). L2 하나를 두 그룹이 같이 쓰고, 파티션과 파티션 사이 연결은 없습니다(항목 68).
- **한 점 돌리기**는 `vortex-exp/`의 스크립트로 합니다. `run_point.sbatch`(Phoenix. 변수 NAME APP ARGS PROFILE CORES XCONF PERF DRIVER), `ice/ice_submit.sh`(같은 변수로 ICE에서. 결과는 `ice/ice_fetch.sh`로 가져옴), `rover/rover_start.sh`(실험실 서버. 같은 변수에 SRC와 MODEL을 더함. `rover_status.sh`가 점과 사이클 수를 보여 줌. 전체 크기 rtlsim은 여기서 200 GB 메모리 slice 안에서, 빌드는 한 번에 하나씩 돌림). 공개 사본은 `study/scripts/run_point.sbatch`와 `study/ice/`입니다.
- **`configure`(그리고 `make software`) 전에 PROFILE이 환경에 있어야 합니다.** 스크립트가 그렇게 합니다. `blackbox --profile`만 쓰면 헤더와 커널 라이브러리가 기본값으로 남습니다(사이클이 약 7% 달라짐. 항목 37, 38).
- **`VORTEX_VM_MEGAPAGE_HEAP=1`**(스크립트의 기본값): 4 KB 페이지면 이 연구의 데이터가 TLB를 벗어나서 페이지 워크를 재게 됩니다.

## 모델을 믿으면 안 되는 곳
- **속도 한계에서의 동작.** SM 입구 제한과 그룹 응답 제한은 측정한 속도에 맞춘 토큰 버킷입니다. 한계에서 요청이 어디서 기다리는지, 어떤 흐름이 어떤 흐름 뒤에서 기다리는지는 제한을 어디에 놓았느냐에서 나옵니다(항목 71). 한계에서의 간섭과 공정성 결과는 독립적인 확인이 필요합니다.
- **파티션과 파티션 사이 연결이 없음.** `h200g2`는 L2 하나를 두 그룹이 같이 쓰고, 파티션 해시도, 가까운/먼 지연도, 복제도 없습니다. SM당 L2는 640 KiB로 실제의 약 465 KiB보다 큽니다.
- **메모리에 묶인 SM이 많을 때의 대역폭.** 최고치가 목표의 85~88%이고, SM 32개 쪽으로 약 6% 떨어집니다. 실제 칩은 평평합니다(항목 69. 2026-11-25에 알려진 한계로 둠).
- **TMA 전송 하나.** 전송 하나를 작업기 하나가 맡아서 클럭당 0.38줄로, 실제의 1.67줄에 못 미칩니다. 지연에 묶인 TMA 결과(CTA가 적고 전송이 하나씩)는 실제보다 느립니다.
- **텐서 유닛 지연.** 시뮬레이션은 TCU 지연 4, 합성 흐름은 5를 씁니다(항목 70).
- **커널은 한 번에 하나.** 같이 도는 두 작업은 CTA가 코어 번호로 역할을 고르는 커널 하나로 흉내 냅니다(`gemm_block`: `bw_cores`보다 번호가 작은 코어의 CTA가 메모리에 묶인 역할). 두 번 실행해서 기계를 나눠 쓰는 것이 아닙니다.
- **DXA를 많이 쓰는 커널의 SimX 대 rtlsim.** CTA 여러 개의 복사와 `gemm_block`에서 SimX가 rtlsim보다 6~7% 빠릅니다(항목 66). 그 차이가 중요하면 rtlsim을 쓰십시오.

## 남은 일, 우선순위 순서
1. DXA를 많이 쓰는 커널의 SimX/rtlsim 차이(복사 7.1%, `gemm_block` 6.2%). 처음 보이는 차이는 DXA 대기열 앞, 워프를 받아들이는 순서(항목 66).
2. TMA 전송 하나가 클럭당 1.67줄 중 0.38줄, 여러 전송의 복사가 105~108 중 80~87바이트. 한 전송의 줄을 두 줄 경로에 나눠 배정하는 설계는 시작하지 않음(항목 64, 67).
3. `h200g2` 2단계의 남은 것: 채널 48개 재배치, 깊어진 L2 출구 경로, 프로파일 검사의 10%를 벗어난 L1과 `h200s` L2 지연(항목 68).
4. 파티션과 파티션 사이 연결(NoC 3단계). 파티션을 넘는 트래픽에 대해 무엇이든 말하려면 먼저 필요함.
5. 작은 SimX/rtlsim 잔차: VM을 끈 워프 16개 dcache(−12.4%, 항목 63), 워프 64개 스택 재현 5.3%(항목 62), 지금 설정에서의 decode 커널 rtlsim 기준값.
6. 합친 설정들의 회로 깊이와 면적, NoC의 합성 타이밍.
